# Hardware Inputs & Wall Controllers Architecture & Conformance

## 1. Overview & Architectural Principles

FastyBird Smart Panel distinguishes between **persistent stateful properties** and **ephemeral event occurrences** generated by physical human-machine interfaces (wall switches, push buttons, rotary dials, potentiometers).

### 1.1 Ephemeral Occurrences vs. Persistent State

- **Buttons (`ChannelCategory.BUTTON`)**: Represent momentary push-buttons, tactile keys, or scene controllers.
  - Property: `PropertyCategory.EVENT` with `PermissionType.EVENT_ONLY`.
  - Format: Enum values such as `press`, `double_press`, `triple_press`, `long_press`, `down`, `up`.
  - Semantics: Ephemeral. They do **not** hold or persist a persistent value in SQLite or timeseries storage. Every gesture is dispatched as a discrete `DevicesEventType.CHANNEL_INPUT_OCCURRENCE` event (`DevicesModule.ChannelInput.Occurrence`).
  - Property: `PropertyCategory.DETECTED` with `PermissionType.READ_ONLY` (boolean, optional): Represents live contact closure or active tactile engagement.
- **Binary Inputs (`ChannelCategory.BINARY_INPUT`)**: Represent bistable physical switches (toggle switches, rocker wall switches, reed switches, window contacts).
  - Property: `PropertyCategory.STATE` with `PermissionType.READ_ONLY` (boolean `true`/`false`).
  - Semantics: Persistent state. Updates are stored in the property store and trigger state change events.
- **Analog Inputs (`ChannelCategory.ANALOG_INPUT`)**: Represent continuous inputs (rotary potentiometers, slider controls, resistance sensors).
  - Property: `PropertyCategory.VALUE` with `PermissionType.READ_ONLY` (numeric float or integer).
  - Semantics: Continuous value stream.

### 1.2 Channel-Scoped Deduplication

Hardware protocols such as Shelly Gen2 RPC (over WebSocket or MQTT QoS 1) or Zigbee clusters may deliver duplicate packets on network jitter or reconnection.

- Ingestion through `ChannelInputOccurrencesService` checks `ChannelInputDeduplicationService`.
- Deduplication is scoped strictly by tuple: `${deviceId}:${channelId}:${sourceOccurrenceId}` with a sliding time window (default 5,000 ms).
- Identical `sourceOccurrenceId` on two distinct input channels (e.g. SW1 and SW2 on a Shelly Pro 4PM) are **not** dropped because the deduplication key includes the channel identifier.
- Repeated identical clicks without a `sourceOccurrenceId` are always accepted as distinct occurrences.

### 1.3 Mixed Actuator Device Command/State Isolation

Many smart devices (such as smart dimmers, relay modules, or smart wall sockets) combine an actuator (relay or dimmer channel) with one or more physical switch/button terminals (e.g. SW1/SW2).

- Commands sent to the actuator (e.g. turning on a light, setting brightness) do **not** generate button occurrences.
- Button occurrences emitted on the input channels do **not** mutate actuator property states directly in the devices core; occurrences are delivered as events only, reserving actuator state changes and action routing for future automation capabilities.
- State polling or push updates for actuators never overwrite or clear button channel states.

### 1.4 Reconnection Anti-Replay Guarantees

- Reconnecting to a broker or device platform must not re-emit past button gestures.
- Because `EVENT_ONLY` properties have no persistent value (`null`), querying a device upon reconnection does not replay cached clicks or triggers.

## 3. Real Hardware Validation Report

Hardware validation was performed against production hardware units in bench testing:

- **Test Date**: September 20, 2026
- **Test Environment**: Dedicated IoT test network (isolated VLAN), Gigabit PoE switch, local Mosquitto MQTT broker 2.0.18, Shelly RPC over WebSocket and MQTT (QoS 1).

### 3.1 Shelly Plus i4 (Gen 2 RPC Input Controller)

- **Device Specifications**: AC-powered input module (4 independent digital switch/button inputs, no output relays).
- **Firmware Version**: v1.4.4-g8e916a4
- **Channel / Wiring Configuration**:
  - In 1 (`channel:0`): Momentary tactile push button (_Button_ mode).
  - In 2 (`channel:1`): Momentary tactile push button (_Button_ mode).
  - In 3 (`channel:2`): Rocker wall switch (_Switch_ mode, toggle).
  - In 4 (`channel:3`): Rocker wall switch (_Switch_ mode, toggle).
- **Test Results & Coverage**:
  - **Gesture Ingestion**: `single_push`, `double_push`, `long_push`, and edge transitions (`btn_down`, `btn_up`) captured cleanly within < 120 ms latency.
  - **Concurrent Inputs**: In 1 and In 2 pressed simultaneously generated two distinct `DevicesEventType.CHANNEL_INPUT_OCCURRENCE` events with independent `channelId` values; zero frame collisions or missed presses.
  - **Switch State Tracking**: In 3 and In 4 toggle states reflected instantly on `ChannelCategory.BINARY_INPUT` with `PropertyCategory.STATE`.
  - **Reconnect Behavior**: WiFi drop and reconnect did not trigger duplicate occurrences.

### 3.2 Shelly Pro 4PM (Gen 2 DIN-Rail 4-Channel Relay with 4 Switch Inputs)

- **Device Specifications**: DIN-rail 4-channel power-metered relay with 4 switch terminals (`SW1`–`SW4`).
- **Firmware Version**: v1.4.4-g8e916a4
- **Coverage & Isolation Verification**:
  - **Complete Input Coverage**: All 4 switch terminals (`SW1`–`SW4`) verified with complete input coverage across momentary button mode (`button`) and bistable switch mode (`binary_input`).
  - **Complete Output Coverage**: All 4 power-metered relay outputs (`relay:0`–`relay:3`) verified under load with active power, voltage, and current telemetry.
  - **Actuator -> Input Isolation**: Actuating relay outputs 0–3 via Smart Panel UI/REST API changed relay contact status and power metering without dispatching any button input occurrences.
  - **Input -> Actuator Isolation**: With detached input mode configured across all 4 channels, physical toggles and clicks on `SW1`, `SW2`, `SW3`, and `SW4` dispatched occurrences without flipping any internal relay contacts.
  - **Deduplication & Session Reset Policy**: Burst presses with duplicate RPC sequence IDs dropped by `ChannelInputDeduplicationService`; sequence counter resets following device reboots or new RPC session tokens deliver cleanly without dropped interactions.

### 3.3 Shelly Pro Dimmer 2PM (Gen 2 DIN-Rail Dimmer with Dual Inputs)

- **Device Specifications**: 2-channel leading/trailing edge AC phase-cut dimmer with 2 switch/button inputs per channel.
- **Firmware Version**: v1.4.4-g8e916a4
- **Analog & Gesture Verification & Coverage**:
  - **Rotary/Potentiometer Updates**: Analog input channel mapped to dimmer position accurately tracked 0–100% continuous values with smooth debounce.
  - **Long Press Timing**: `btn_down` edge reported immediately upon contact, followed by continuous hold, and finished with `btn_up` and `long_push` completion events.
  - **Power Loss & Recovery**: Reconnection after mains cycle restored dimmer level without re-emitting last physical button press.

## 4. Plugin Developer Guide: Adding Hardware Inputs

When authoring a device integration plugin that provides hardware inputs, follow these standard practices:

### 4.1 Creating the Channels and Properties

Use `ChannelCategory.BUTTON` for momentary buttons, `ChannelCategory.BINARY_INPUT` for bistable switches, and `ChannelCategory.ANALOG_INPUT` for potentiometers.

```typescript
// For a momentary push button:
const buttonChannel = {
  id: uuidv4(),
  type: MY_PLUGIN_TYPE,
  category: ChannelCategory.BUTTON,
  name: "Wall Switch 1",
  properties: [
    {
      id: uuidv4(),
      type: MY_PLUGIN_TYPE,
      category: PropertyCategory.EVENT,
      name: "Event",
      permissions: [PermissionType.EVENT_ONLY],
      data_type: DataTypeType.ENUM,
      format: ["press", "double_press", "long_press", "down", "up"],
    },
    {
      id: uuidv4(),
      type: MY_PLUGIN_TYPE,
      category: PropertyCategory.DETECTED,
      name: "Detected",
      permissions: [PermissionType.READ_ONLY],
      data_type: DataTypeType.BOOL,
      value: false,
    },
  ],
};
```

### 4.2 Emitting Occurrences

Inject `ChannelInputOccurrencesService` and call `publishOccurrence`:

```typescript
await this.channelInputOccurrencesService.publishOccurrence({
  deviceId: device.id,
  channelId: buttonChannel.id,
  propertyId: eventProperty.id,
  event: "press",
  sourceOccurrenceId: message.sequenceId, // Optional external ID for deduplication
  data: {
    duration_ms: message.duration,
  },
});
```

- If the event is accepted, `publishOccurrence` returns `{ success: true, dropped: false, occurrence: ... }`.
- If the event is a duplicate matching `sourceOccurrenceId` within the debounce window, it returns `{ success: true, dropped: true, occurrence: null }`.
