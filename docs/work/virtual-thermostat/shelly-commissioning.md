# Shelly thermostat installation workflow

This workflow stages a reviewable artifact and records expected installation metadata, separately from operator commissioning attestations. The backend never deploys a script, changes Shelly configuration, reboots the device, or certifies physical equipment. An installed profile does not contain an OFF/drain proof. The runtime must still obtain a fresh matched persistent-epoch fence and live OFF readback before permitting ON.

Migration 33 persists a typed profile per retained actuator claim and an append-only revision/actor/time audit. Migration 34 separately implements recovery and rotates the claim qualification generation. Updates require the current installation revision, synchronously revoke all captured ON authority and qualification before the first lock/database await, hold admission closed through commit or rollback (including CAS failure), and request runtime safety release. Reservations survive revocation. Startup never trusts a persisted `metadata_verified` observation: it rereads the actual captured managed device identity/FW, every script code chunk and SHA256, nonce-correlated HTTP status, floor configuration, SensorAddon peripheral identity, and switch configuration. Connection, configuration and structure changes revoke the captured lease synchronously. A durable safety fingerprint covers floor limit/hysteresis, branch presence, timers/contact/heuristic policy, source/freshness/calibration metadata, all opposed claims/leases and recovery generations. Ordinary mode/setpoint edits within the explicit installed ranges reuse equipment attestations only after fresh metadata verification and a new runtime fence for the current configuration revision. Expanded comfort ranges or safety/source/claim changes require re-staging; they never silently expand eligibility. ON/fence dispatch rereads those expected metadata prerequisites, so a changed floor peripheral or switch writer configuration cannot borrow a previous barrier.

Ordinary comfort controls use the registered local thermostat command batch and preserve unchanged claim revisions. The full configuration PUT is an authoring action: it advances claim revisions and intentionally requires installation re-staging, even if an editor changed only a setpoint. This does not bypass the claim fence.

An identified OWNER/ADMIN user session (API/machine tokens are refused even when owned by an administrator) can use the existing authenticated API or:

```sh
export SP_API_URL=http://127.0.0.1:3000
# Supply an existing owner/admin user-session access credential through the environment, without printing it.
node scripts/thermostat-installation.mjs stage CLAIM_UUID 0 equipment.json
node scripts/thermostat-installation.mjs inspect CLAIM_UUID
node scripts/thermostat-installation.mjs artifact CLAIM_UUID ./reviewed-guard.js
node scripts/thermostat-installation.mjs verify CLAIM_UUID 1
node scripts/thermostat-installation.mjs revoke CLAIM_UUID 1
```

`equipment.json` accepts only `setup` and `operator_attestations`. Setup explicitly supplies hardware ID, exact full firmware ID, managed fixed-IP endpoint, a separately approved script slot and persistent epoch KVS key, explicit heating/cooling comfort setpoint ranges (null only for an absent branch), tested min/max lease seconds, watchdog period, original floor sample maximum age, the physical floor component type/id/attribute, and exact readonly `floorConfigurationJson`, `switchConfigurationJson`, and `peripheralsJson` snapshots. No thermal calibration, timing or equipment limit is filled by default. The source binds the configured floor protective limit and strict recovery hysteresis. For calibrated voltage, `floorConversion` requires `kind: steinhart_hart`, referenceVoltage, seriesResistance, a/b/c, thermistorLeg, and inputRange/outputRange; each must equal the reviewed backend Steinhart–Hart transform policy and domains. Native Celsius helper expressions are metadata and are never evaluated by the backend.

Each attestation has an explicit kind, equipment, procedure, evidenceReference, dated testedAt and optionally maximumObservedMs. Required kinds are commissioning_barrier, writer_isolation, restart_drain, local_execution_bounds, endpoint_authentication, and independent_protection; opposed outputs additionally need opposed_interlock. The measured local execution bound must fit the explicit watchdog budget. These records are privileged **human attestations**, never machine evidence of electrical isolation or physical OFF. Responses always expose `physical_safety_certified: false`. Public qualification booleans and supplied drain/OFF proof objects are rejected. Incomplete attestations can be staged for review but cannot initialize runtime eligibility. Staging always clears server-owned activation intent; complete attestations alone never arm ON. Only successful explicit user-session `verify` records durable activation intent and its actor audit, after all machine metadata checks succeed. Startup/reconnection can renew that already armed intent using fresh verification; they cannot arm a newly staged profile. Revocation clears activation intent. Native automatic ON, unsafe restart state or an unlocked non-detached physical input remain blockers even with an attestation.

The artifact and its expected hash are persisted for review; a changed packaged implementation requires a new reviewed profile rather than silently accepting old installed code. `verify` is an explicit privileged activation action. It revokes prior eligibility before its first await, reads machine metadata, commits activation/audit, and only then resumes the configured runtime, which may issue safety OFF/fence and then honor intent after all safety gates. Staging/revocation also request runtime safety release. Those effects are explicit product actions. Device writes and bench testing are separate installation actions requiring approval of the concrete reviewed artifact and procedure. The CLI sends only panel API requests; stage/revoke/accepted verification can trigger the documented backend runtime release/intent actions.

The known pilot is Plus1PM SNSW-001P16EU, firmware `20260311-095847/1.7.5-g9979d16`, and already has Script 1 `NTC Conversion`. Preserve that script. Its observed conversion constants are Vref=10 V, Rseries=10000 ohm, A=0.0010351024725298568, B=0.0002338353574079741, C=7.917851073336009e-8, low thermistor leg. They do not establish the permissible floor limit, watchdog budget, calibration domains or physical protection. The existing script logs converted voltage every 30 seconds and cuts off strictly above 30 C; missing/invalid input and equality are insufficient protection. The supplied device currently has an unlocked follow input and disabled native automatic OFF. No installed candidate code, qualified external writer barrier, sensor equal-report cadence, measured bounded native IO/restart drainage, endpoint isolation, independent protective hardware, or opposed interlock has been certified.

Before approving an installation action, the operator must review the exact artifact/hash/slot, preserve existing scripts, identify wiring and independent limit equipment, describe exclusion of physical input/cloud/MQTT/other scripts/native RPC writers, test queued ON versus persisted fence/restart under the exact firmware, measure bounded local OFF/readback and watchdog behavior, and establish original sensor report cadence and failure behavior. These software and offline VM/SQLite tests do not replace that evidence. Missing-device recovery is the separate retained-claim workflow; restoring a claim rotates its generation and old profiles cannot regain eligibility across restart.
